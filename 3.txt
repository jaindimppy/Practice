What is the difference between Deferred (Lazy) Execution and Immediate Execution in LINQ?
Answer: Deferred Execution means the query is not evaluated when constructed; it executes only when the data is iterated over (e.g., using a foreach loop). Immediate Execution forces the query to evaluate immediately and cache results (e.g., using .ToList(), .ToArray(), or .Count()).

What is the "N+1 Query Problem" in EF Core, and how do you prevent it?
Answer: It happens when code loads a parent entity and then fires a separate database query for each child entity inside a loop. You prevent it by using Eager Loading with the .Include() and .ThenInclude() methods to fetch all required data in a single SQL JOIN statement.

When and why would you use .AsNoTracking() in Entity Framework Core?
Answer: You use it for read-only queries. It tells EF Core not to waste CPU and memory tracking changes on the fetched entities, significantly improving performance for search results or report views.


Azure Managed Identity vs. Connection Strings
What is Azure Managed Identity?
Managed Identity eliminates the need for your code to maintain credentials (like passwords, client secrets, or connection strings).
No Credential Exposure: You don't store passwords or access keys in your appsettings.json, environment variables, or Azure App Configuration. Even if your source control or server config is leaked, there are no secrets to steal.
Automatic Lifecycle & Rotation: Microsoft handles credential rotation completely under the hood. You never have to worry about an app breaking because an expiring secret wasn't updated.
Granular Access Control (RBAC): You grant specific Azure permissions to the identity itself. For example, your App Service identity can be granted only Azure SQL Data Reader and Data Writer roles—nothing more.

What is the difference between Eager Loading, Explicit Loading, and Lazy Loading?
Answer: * Eager Loading: Fetches related data along with the main entity in a single query using .Include() (e.g., loading an Order along with its OrderItems via a SQL JOIN).
Explicit Loading: Loads related data explicitly at a later point after the main query has executed, using context.Entry(order).Collection(o => o.OrderItems).Load().
Lazy Loading: Delays the loading of related data until the navigation property is accessed for the first time in code. It relies on proxy runtime wrappers and can easily trigger performance bugs (like the N+1 query problem) if not used carefully.

Explain Await() and Wait or Result()
The Right Way: Using await
When a Chef uses await for a database query:
The Chef puts the cake in the oven.
Because it is awaited, the Chef walks away and helps another customer or prepares another order.
When the oven timer goes off (the database returns data), any available Chef comes back to finish the cake.
Result: The kitchen runs efficiently. Even with only a few Chefs, hundreds of orders move smoothly because no one is standing around idle.

1. The Healthy Async Flow (await)
When a request comes in, a thread is assigned to handle it. If that request needs to perform an asynchronous I/O operation (like fetching data from a database or calling a third-party API) and uses the await keyword:
The thread kicks off the database task and is immediately released back to the thread pool.
While the database is busy working, that thread is free to handle other incoming user requests.
When the database finishes, a thread is pulled from the pool to resume your method.
Result: High throughput. A small number of threads can handle thousands of concurrent users.

2. The Choking Sync Flow (.Result / .Wait())
When a developer calls a background async method but forces it to run synchronously using .Result or .Wait():
The assigned thread kicks off the database task.
Instead of releasing itself, the thread blocks and stands completely still, crossing its arms and waiting for the database to return a value.
Under heavy traffic, if 100 users hit endpoints that use .Result, 100 threads are instantly frozen and locked up.

Find() — Synchronous (Blocking)
How it handles the thread: The thread handling the web request tells the database: "Go find the user with ID 5." While the database is searching the disk, that thread blocks (freezes) and stands completely still. It cannot do any other work until the database returns the data.

FindAsync() — Asynchronous (Non-Blocking)
How it handles the thread: The thread tells the database: "Go find the user with ID 5." Because it is awaited, that thread immediately releases itself and goes back to the thread pool. It can now handle new incoming requests for other users. The moment the database finishes finding the record, an available thread from the pool wakes up and resumes your code.

.net core request pipeline-sequence of middleware
The ASP.NET Core request pipeline is configured using a series of middleware components executed sequentially in a bidirectional 'U-turn' architecture. Each component receives an HttpContext and handles logic on both the inbound request and outbound response phases.
The ordering of components inside Program.cs is critical; middleware handles tasks like exception safety, CORS validation, routing, and authentication before passing execution to the terminal endpoint map. Any middleware component can cleanly short-circuit the pipeline by generating a response and returning early without invoking the next delegate.
